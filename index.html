The argument

Four moves

01 — THE IDEA

A question, not a project

"I want to ask things of clinical data."

No platform decision yet. No budget. Just the question.

02 — THE TOOL

Someone already built it

m3 — a server for MIMIC-IV clinical data — is built and maintained by colleagues at MIT. I'm a contributor, not its author.

And to use it here I didn't fork it, wrap it, or ask them to change anything. It already spoke the protocol. That's what a shared standard buys you: tools owned by different teams, on different roadmaps, composed without a negotiation.

03 — THE AGENT

Tools aren't enough

An agent needs an identity, somewhere to run, and rules about what it may do unsupervised.

It becomes ordinary infrastructure — same deployment, same access control, same review as everything else. Including a gate: some actions stop and wait for a person.

04 — NO NEW PLATFORM

Stay where you work

The agent platform speaks the same protocol as the tools, so Claude Code drives all of it.

No new console to learn, nothing to migrate into. The agent shows up beside the tools I already had.

The point

Nothing here was written from scratch. A clinical data server maintained by another team, an off-the-shelf gateway, and a governance layer that already existed — composed into something you can point at real data and trust not to act alone. That's the distance from an idea to an agent.

The demo

Two prompts

Both typed into Claude Code — no special console. They're a pair, and the difference between them is the whole point: the first runs instantly with nobody asked, the second stops dead.

✅ no approval Prompt 1 uses a pre-reviewed tool. A human wrote and checked that query before it ever shipped, so the agent may run it freely.
⛔ approval required Prompt 2 makes the agent write its own query against patient records. Nobody has read it. So it stops.

Same database. Same agent. The gate isn't about how risky the data is — it's about who wrote the question.

Prompt 1 — the borrowed tool runs freely

Ask a question of the data

The server answering this is maintained by another team. I connected to it as-is.

Show me the race distribution across hospital admissions.

Watch for: real numbers, immediately — nobody was asked for permission. That's deliberate. Reached through a server maintained by another team, at another institution, running unmodified.

Prompt 2 — the gate stops and waits

Ask something it has to think about

No pre-built answer exists for this, so the agent has to write its own database query — over patient records.

Ask kagent/clinical-ops-agent whether Medicare patients have longer ICU stays than Medicaid patients.

Watch for: it explores the data, writes a query — and then stops. Nothing runs. The platform holds the request until a human approves it, with the exact query on screen to read first.

Why this one matters

Nothing here was destructive — it's a read. It paused because a language model wrote a query against patient records thirty seconds ago and nobody had looked at it yet. That isn't the model choosing to be careful. It's the platform refusing to let it through.

Try it yourself — a personal agent, in a minute

You don't need any of the infrastructure above to start. In Claude Code, just describe the agent you want in plain English and it writes the definition for you:

Create a subagent that reviews my pull requests for security issues.
Save it to ~/.claude/agents/ so I can use it in any project.

That's it — a file appears at ~/.claude/agents/ and the agent is available immediately. No console, no deployment, no approval from anyone.

Then give it tools

An agent with no tools can only talk. Adding one is a single command — this is exactly how the clinical data server got connected in this demo:

claude mcp add --transport http my-tools https://example.com/mcp

Check it with /mcp. That's the whole extension model: the agent you wrote in a sentence can now reach anything that speaks the protocol.

Share it — plugins and marketplaces

Once an agent is useful, the next question is how a colleague gets it. Claude Code packages agents, skills and tool connections into a plugin, and any Git repo can act as a marketplace. Two commands for whoever you share it with:

/plugin marketplace add your-org/your-repo
/plugin install your-plugin@your-marketplace

On your side it's one file — .claude-plugin/marketplace.json at the repo root — listing the plugins it offers. The plugin itself is just a folder with agents/, skills/ and an optional .mcp.json. Full structure in the technical detail.

Worth knowing

Plugins run with your privileges and hooks execute without prompting — only add marketplaces you trust, exactly as you'd treat any dependency.

Scale it — the same pattern, centrally

A personal agent is yours alone. The moment several teams share one — or it touches regulated data — you need the things this demo shows: somewhere to run, an audit trail, and a gate. That's the only real difference between the two ends.

The shape doesn't change with the vendor. Tools, an agent, and a governance layer. Whatever your organisation already runs, there's an equivalent — so what you learn in Claude Code on your laptop transfers:

kagent — used in this demo Agents as Kubernetes resources. Created at Solo.io, now a CNCF sandbox project, Apache 2.0. Where the approval gate you just saw comes from. AWS — Amazon Bedrock AgentCore Build, deploy and run agents with any framework or model, with identity and observability handled. Microsoft — Foundry Agent Service Part of Microsoft Foundry. Agents that automate business processes "while keeping humans in control". OpenAI — Agents SDK Manages the agent loop, multi-agent orchestration, sessions, tracing and guardrails. Anthropic — Claude Agent SDK The same harness Claude Code is built on, for building your own agents. MCP — the common layer The one piece shared across all of the above. Tools you connect today keep working if the platform changes.
Why this is reusable

Every platform above solves the same three problems in the same order — connect tools, give the agent somewhere to run, decide what it may do unattended. Pick whichever your organisation already uses. The one thing worth standardising on is the tool layer, because that's what you'd otherwise rewrite every time the platform underneath changes.
