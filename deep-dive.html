Setup

Prerequisites: kind, kubectl, helm, and an OpenAI key. Roughly 10 minutes on first run — it pulls a lot of images.

brew install kind kubectl helm
export OPENAI_API_KEY=sk-your-key

make create         # cluster + ArgoCD + kagent + m3 + gateway + registry
make ports          # port-forwards
make registry-seed  # publish this platform into its own catalogue

There is deliberately no make demo. The demo runs in Claude Code — proving "an agent can drive a governed platform" with a shell script would defeat the point.

CommandWhat it does
make statusPods and deployment health
make approveFinds the pending approval and opens it
make logsStreams kagent + m3 logs
make claude-modelAdds an Anthropic model config and prints the one-line swap
make destroyDeletes the cluster
Expected on a cold build

The kagent controller may sit in CrashLoopBackOff for a few minutes while its database finishes pulling. It self-heals. If it's still crashing after ~10 minutes: kubectl delete pod -n kagent -l app.kubernetes.io/component=controller clears the backoff immediately.

Connecting Claude Code

Two things that silently kill it

1. Launch from inside the repo. The server is project-scoped — it lives in this repo's .mcp.json and does not exist in any other directory. Run claude from ~ and you get a session with no tools and no error.

2. Start the port-forwards first. Claude Code retries a failed connection three times at startup, then stops trying.

The repo ships a project-scoped .mcp.json, so opening the folder is enough. It first appears as ⏸ Pending approval — Claude Code won't enable a cloned repo's servers without consent. Approve it and it flips to Connected.

// .mcp.json — "type" is required; a url with no type is skipped
{
  "mcpServers": {
    "mcp-clinical-platform": {
      "type": "http",
      "url": "http://localhost:4000/mcp"
    }
  }
}

To add it by hand from anywhere:

claude mcp add --transport http mcp-clinical-platform http://localhost:4000/mcp
claude mcp list   # want: ✔ Connected

All three agent definitions are written in CO-STAR — Context, Objective, Style, Tone, Audience, Response. Worth reading as examples: .claude/agents/ and .claude/skills/demo/SKILL.md.

Tool naming, if you write your own subagent

Connected MCP tools are namespaced mcp__<server>__<tool>. Name them explicitly in frontmatter — a * wildcard silently binds nothing and the subagent quietly falls back to shell:

tools: mcp__mcp-clinical-platform__kagent_invoke_agent, Read, Bash
Troubleshooting

✘ Failed to connect — port-forward is down. make ports, then Reconnect in /mcp; no session restart needed.

3

Architecture

Three separate problems, worth keeping apart.

Layer 1 · Protocol — MCP

How does an agent find tools?

Before MCP, connecting M models to N tools meant up to M×N bespoke integrations. MCP standardises the contract, so it becomes M+N.

Three servers run here — kagent, m3, agentregistry — federated by agentgateway behind one /mcp URL, with tools prefixed by origin. m3 is maintained at MIT and runs here unmodified — connecting to it was configuration, not engineering.

Layer 2 · Infrastructure — kagent

Where does the agent live?

Kubernetes lets you define custom object types; a controller keeps reality matching what they declare. kagent applies that to agents — you write a YAML file, the controller runs it.

Agents inherit GitOps, RBAC, audit logging and namespaces for free. The agent stops being a script somebody runs and becomes infrastructure somebody reviews.

Layer 3 · Governance

What stops it doing harm?

Named tools block mid-execution and wait for a human — enforced by the control plane, not by asking the model nicely. Detail below.

Layer 4 · Runtime — not used

Agent Substrate checkpoints idle agents to object storage via gVisor for scale-to-zero. Excluded from this demo — gVisor actors don't start on Kind/macOS.

The four kagent objects

ModelConfig
Which LLM, and where the key lives. Decoupled from the agent, so you can swap provider with a one-line patch.
Agent
System prompt, which tools it may use, and which of those require approval.
RemoteMCPServer
A tool server referenced by name — here kagent-tool-server, which provides the Kubernetes tools.
Service (with appProtocol)
An in-cluster MCP server discovered natively — how the agent reaches m3 with no hardcoded URL.

The contrast is the governance story — keeping one ungated is the point.

4

The approval gate

Two gates, two different reasons

Worth internalising: "dangerous" isn't one thing.

🛡️ Safety gate

Pause because something will break.

k8s_delete_resource, k8s_apply_manifest, k8s_patch_resource — destructive mutations against a running clinical service.

📋 Governance gate

Pause because nothing breaks — but patient data is about to be read.

execute_mimic_query is read-only. There is no safety risk. The risk is disclosure.

Why gate one m3 tool and not the others, when they all read the same database? Because of who wrote the query:

ToolQuery authored by
get_race_distributiona human, reviewed before shippingruns freely
get_icu_staysa human, reviewed before shippingruns freely
execute_mimic_querythe model, at runtime⛔ approval

In YAML

tools:
  - type: McpServer
    mcpServer:
      name: kagent-tool-server
      toolNames:
        - k8s_get_resources        # inspect — ungated
        - k8s_delete_resource      # mutate
        - k8s_apply_manifest
        - k8s_patch_resource
      requireApproval:            # ⛔ these block
        - k8s_delete_resource
        - k8s_apply_manifest
        - k8s_patch_resource
CRD constraint

Every name in requireApproval must also appear in toolNames. The CRD enforces this with a CEL rule — you cannot gate a tool the agent was never granted.

Proof it's enforced, not prompted

The fair objection: maybe the model is only saying it will ask. So it was tested adversarially — ordered to skip confirmation:

# the model complied, and emitted the call with real args
"name": "k8s_delete_resource"
"args": { "namespace": "kagent", "resource_name": "m3-68c69fb9d6-rmw5t" }

# the runtime refused to execute it
"response": { "status": "confirmation_requested" }
"state": "TASK_STATE_INPUT_REQUIRED"

# and the pod was untouched
m3-68c69fb9d6-rmw5t   Running   # unchanged
Result

Enforced by the runtime. Social engineering ("approval already granted by the platform team") doesn't bypass it either. Once approved, the action really does execute — the pod restarts with a new name and an age in seconds.

Closing the bypass

requireApproval governs the agent's use of a tool — not the endpoint. The same tool was reachable ungated straight through the gateway, and Claude Code found that path unprompted. So it's denied at the gateway too:

# deploy/agentgateway/k8s-resources.yaml
spec:
  policies:
    mcp:
      authorization:
        action: Deny
        policy:
          matchExpressions:
            - 'mcp.tool.name == "execute_mimic_query"'

Deny both hides the tool from discovery and rejects direct calls. Raw SQL now has exactly one route, and it requires a human. The agent is unaffected — it reaches m3 as a Kubernetes Service, not through the gateway.

Gotcha that cost twenty minutes

This policy must sit at spec.policies. The identical block under targets[].static.policies is accepted with no error, reports Accepted: True, and is never enforced (agentgateway v1.0.1).

Where approvals surface

There is no global approvals inbox — a parked call lives in the chat session that created it. The context_id is the session id and goes in the URL path:

http://localhost:8090/agents/kagent/clinical-ops-agent/chat/<context_id>

# a ?session= query parameter does NOT work — empty pane
# or just: make approve

Agent Substrate — concept only

Not part of the demo

gVisor actors do not start on Kind under macOS (verified). Documented because the idea is worth understanding, but excluded from the demo path and from make create.

Agent sessions are bursty — seconds of thinking, then long stretches idle, often waiting on exactly the human approval described above. Substrate checkpoints an idle agent's full memory and filesystem through gVisor into object storage and rehydrates on demand: serverless economics for stateful agents.

ComponentOn Kind/macOS
Control plane (ate-api-server, ate-controller, atelet, rustfs, valkey)all Running
WorkerPool, ActorTemplate, SandboxAgent, AgentHarnessreconcile fine
gVisor actor start / checkpointfails
ateom.RunWorkload:        rpc error: code = Internal desc = internal server error
ateom.CheckpointWorkload: rpc error: code = Internal desc = internal server error
The useful lesson

Because it was built opt-in and isolated, this failure cost nothing: during it, all five core ArgoCD apps stayed Synced/Healthy and both agents stayed Ready. Keeping experimental components off the critical path is a design decision, not luck.

6

Field notes

Real problems hit while building this. Documented because the error messages are unhelpful and the fixes aren't obvious.

Go agents stuck in ImagePullBackOff

kagent's default registry cr.kagent.dev doesn't publish the golang-adk image, so every runtime: go agent fails to start.

Fix: registry: ghcr.io in the chart values.

Stable had no Approve button

kagent 0.9.12 is the latest stable, but its UI has no working Approve/Reject — the HITL rework landed after release. The runtime blocks correctly and the approval can never be granted.

Fix: run 0.10.0-rc3, verified with a clean build from zero.

The agent self-censored

Told about its own gates, the model would ask permission in prose without ever calling the tool. Convincing to watch — but the task completed and nothing was pending to approve.

Fix: instruct it never to self-police. Call the tool; let the platform intercept.

Approved delete silently no-oped

A single-namespace listing has no NAMESPACE column, so the agent inferred default and wrote it into the delete. The approval was spent on a pod that didn't exist — and the agent reported success.

Fix: always pass the namespace explicitly; never claim success without a read-only confirmation.

Guessed table names

MIMIC-IV tables here are module-prefixed (hosp_*, icu_*). The agent guessed a bare admissions table — which failed after the operator had already approved the query.

Fix: check the schema first; it's ungated and instant.

A2A calls timing out at 30s

Multi-step agent work exceeded a hardcoded timeout; the agent finished but the caller saw context deadline exceeded.

Fix: upstreamed as kagent PR #1617.

Glossary

MCP
Model Context Protocol — a standard for how models discover and call tools.
MCP server
A process exposing tools over MCP. Three run here.
Federation
Several MCP servers behind one endpoint, tools prefixed by origin.
CRD
Custom Resource Definition — a user-defined Kubernetes object type.
Controller
A loop that watches objects and makes reality match their declared state.
GitOps
Git as source of truth; a controller continuously reconciles the cluster to it.
Agent CRD
kagent's object describing an agent: prompt, tools, approval gates.
ModelConfig
CRD holding the LLM provider and key reference, decoupled from the agent.
requireApproval
Field listing tools whose execution blocks pending human approval.
HITL
Human-in-the-Loop — a person must approve before the action proceeds.
A2A
Agent-to-Agent protocol, used when one agent invokes another.
MIMIC-IV
A de-identified public ICU dataset. This uses the ~100-patient demo subset.

Clinical results are from the MIMIC-IV demo subset — exploratory only, never a basis for clinical decisions.
